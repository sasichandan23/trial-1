The problem

Your reviewer has amnesia

Review bots get switched off because the noise outgrows the signal. Not because they are wrong, but because they never learn anything about you.

↻

It repeats itself

You rejected that suggestion in March. It will make it again in April, and in May, in exactly the same words.

?

It doesn't know your rules

"We don't type-hint private helpers" is a decision that exists nowhere in your code. A model reading the diff cannot infer it.

!

It has never seen you fail

The pattern that took checkout down last quarter looks like ordinary code to a reviewer with no history.

How it works

The model is stateless. The memory is not.

The review itself is ordinary. Everything interesting happens either side of the model call.

01

Recall before reviewing

A query built from the diff pulls back what this team has already decided: conventions, past feedback, rejected suggestions, and incidents tied to code patterns. Capped at about 1,000 tokens, so the prompt never grows with the bank.

02

Review with those as rules

Memories enter the prompt under headings the model treats as binding, not as background reading. Findings come back citing the precedent behind each one.

03

Retain what happened next

Accept a finding, reject it, state a rule, or record an incident. Each response is written back. The bank compounds with every pull request, and so does the reviewer.

✓

Feedback

How a reviewer answered a specific finding, and why. Rejections carry the most signal of anything stored here.

§

Conventions

Team rules, stored as standing directives so they apply to every review rather than only to similar-looking diffs.

⚠

Incidents

A bug or outage tied to a code pattern, matched later on the shape of the bug rather than its wording.

≡

Reviews

A summary of everything it has already said, so it does not say it twice.

Get started

Running in about two minutes

One free account for the memory, one free key for the model. Or neither, if you run it entirely on your own machine.

01Install

$ pip install git+https://github.com/WaifuPuller/MemoLint

02Two free keys, no card

Hindsight holds the memory. Groq writes the reviews. Both go in a file called .env in the directory you run memolint from, which is normally the root of the repository you are reviewing.

# your-project/.env
HINDSIGHT_API_KEY=hsk_...   ← ui.hindsight.vectorize.io
GROQ_API_KEY=gsk_...        ← console.groq.com/keys

03Check it connected

Creates the memory bank for this repository. If a key is wrong, this is where you find out.

$ memolint init
Bank ready: memolint-your-org-your-repo

04Review

$ memolint review --git main..HEAD        # a branch
$ memolint review --diff changes.diff      # a patch file
$ memolint review --pr owner/repo#42 --post # a real PR, posts comments

05Teach it — this is the part that compounds

$ memolint feedback F2 --reject --note "we do not type-hint private helpers"
$ memolint teach "prefer guard clauses over nested ifs"
$ memolint incident "N+1 in checkout caused the Sept 3 outage"

06See what it knows

$ memolint memories
$ memolint ask "what does this team care about in reviews?"

01One line, nothing installed permanently

$ claude mcp add memolint -- uvx \
    --from git+https://github.com/WaifuPuller/MemoLint memolint-mcp

02Give it your key

Goes in .mcp.json at the root of your project, so the whole team picks it up from version control. Put it in the server's own config rather than a .env file: the agent launches the server from whatever directory it likes, so a file is not reliably found. An environment variable always is.

// your-project/.mcp.json
{
  "mcpServers": {
    "memolint": {
      "command": "memolint-mcp",
      "env": { "HINDSIGHT_API_KEY": "hsk_..." }
    }
  }
}

03Then just talk to it

No commands to learn. The agent decides when to reach for memory, and you teach it in the same breath as everything else.

> review my changes before I open a PR
> what does this team think about error handling?
> remember that we always use guard clauses here
> that suggestion was wrong, we don't type-hint private helpers
> the Sept 3 outage was an N+1 in checkout, remember that

04What changes

The agent calls recall_team_memory before it writes code, so it follows your conventions the first time instead of being corrected afterwards. It can also store a rule when you state one, log an incident, and run a full review on demand.

05Confirm it is wired up

Ask Claude Code a question only the memory can answer. If it calls the tool, you are done.

> what does this team care about in reviews?
  → calls recall_team_memory
Nothing is hosted. The client runs the server as a local process over pipes. The only remote piece is the memory bank itself.

03Cursor, Windsurf, Antigravity

Each keeps its MCP servers in its own JSON file. Search that client's settings for "MCP" to find it, then paste the block below. The shape is identical everywhere; only the file location differs, and we would rather you check than we guess wrong.

{ "mcpServers": { "memolint": {
    "command": "memolint-mcp",
    "env": { "HINDSIGHT_API_KEY": "hsk_..." } } } }
MCP is an open standard, so one server works with every client that speaks it. Six tools are exposed, including recall, teach, and full review.

Two different things are worth separating here. OpenClaw agents can get long-term memory from Hindsight directly, through an official plugin that Vectorize maintains. MemoLint is a separate tool that reviews code using the same memory system. You can run either, or both against the same bank.

01Give OpenClaw agents memory — official Hindsight plugin

$ openclaw plugins install @vectorize-io/hindsight-openclaw

02Run its setup wizard

Offers three modes: Hindsight Cloud, an external API, or an embedded local daemon that bundles the memory engine and its database into one process.

$ npx --package @vectorize-io/hindsight-openclaw hindsight-openclaw-setup
$ openclaw gateway

03Add MemoLint for code review

MemoLint speaks MCP, so any client that supports it can reach the same memory bank. Use the Codex and Cursor tab for the config shape.

$ pip install git+https://github.com/WaifuPuller/MemoLint
The plugin commands above are Vectorize's, from the Hindsight integration docs, not ours. We have not tested MemoLint's MCP server inside OpenClaw specifically. Check whether your OpenClaw version supports MCP clients before relying on step three.

No API keys, and no source code leaves your machine. Ollama runs the model, Hindsight runs in Docker. For regulated codebases, or anywhere code cannot go to a third party.

01Memory, self-hosted

$ docker run -it --pull always --name hindsight \

    -e HINDSIGHT_API_EMBEDDINGS_PROVIDER=local \
    -v hindsight-data:/home/hindsight/.pg0 \
    ghcr.io/vectorize-io/hindsight:latest

02Model, local

$ ollama pull qwen2.5-coder:7b

03Point at both

Same .env in the repository you are reviewing. No keys needed at all in this mode.

# your-project/.env
HINDSIGHT_BASE_URL=http://localhost:8888
LLM_PROVIDER=ollama
Hindsight needs a model with structured output support for its own fact extraction. A local model handles it, at some cost to extraction quality.
Who sees what

Your memory is yours

The server runs on your machine and stores nothing. The memory lives in a Hindsight bank, and the key you use decides which bank you reach. That one fact answers most questions about privacy and sharing.

1

Trying it alone

Your own free key, your own empty bank. It learns from you and nobody else can read it. Installing from a public repo never exposes anyone else's memory.

N

Sharing across a team

Everyone uses a key from the same Hindsight account. One rule your colleague teaches it shows up in your next review, because you are both reaching one bank.

⌂

Code that cannot leave

Run Hindsight yourself in Docker and point everyone at that URL. Pair it with a local model and nothing touches a third party at all.

Separate accounts mean separate banks, even when the repository is the same. Memory is shared because the Hindsight instance is shared, not because the tool is installed.
