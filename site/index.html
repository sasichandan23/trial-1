Get started

Pick how you want to run it

Everything below works on free tiers. The only required account is Hindsight, which stores the memory. Choose the path that matches your setup.

1. Install

$ pip install git+https://github.com/WaifuPuller/MemoLint

2. Get two free keys

A Hindsight key from ui.hindsight.vectorize.io for the memory, and a Groq key from console.groq.com/keys to write the reviews. Neither needs a card.

# .env in your project
HINDSIGHT_API_KEY=hsk_...
GROQ_API_KEY=gsk_...

3. Review something

$ memolint review --git main..HEAD
$ memolint review --pr owner/repo#42 --post

4. Teach it

This is the part that matters. Rejections carry more signal than anything else it stores.

$ memolint feedback F2 --reject --note "we do not type-hint private helpers"
$ memolint teach "prefer guard clauses over nested ifs"
$ memolint incident "N+1 in checkout caused the Sept 3 outage"

One line

MemoLint ships an MCP server, so the agent that writes your code can consult the same memory before it writes. Nothing is installed permanently.

$ claude mcp add memolint -- uvx --from git+https://github.com/WaifuPuller/MemoLint memolint-mcp

Then add your Hindsight key

# .env in your project
HINDSIGHT_API_KEY=hsk_...

What changes

The agent is told to call recall_team_memory before writing code, so it follows your conventions the first time instead of being corrected afterwards. It can also store a rule when you state one, record an incident, and run a full review.

Nothing is hosted. The client launches the server as a local process and talks to it over pipes. The only remote piece is the memory bank.

Install the server

$ pip install git+https://github.com/WaifuPuller/MemoLint

Codex

Add to ~/.codex/config.toml:

[mcp_servers.memolint]
command = "memolint-mcp"

Cursor, Windsurf, Antigravity and others

Same shape, in each client's own MCP config file:

{
  "mcpServers": {
    "memolint": { "command": "memolint-mcp" }
  }
}
MCP is a standard, so one server works with every client that speaks it. Check your client's docs for where its config file lives.

What it is

The model is stateless. The memory bank is not.

MemoLint reviews a diff, a branch, or a pull request. That part is unremarkable. What matters is what happens either side of the model call.

  1. Recall. Before reviewing, it queries a memory bank for what this team has decided that bears on this change, budgeted to about 1,000 tokens.
  2. Review. Those memories go into the prompt under headings the model is told to treat as binding rules, not as background context.
  3. Retain. Afterwards, and once a human responds, it writes back what happened. The bank grows with every pull request.

Four kinds of memory

KindWhat it isWhy it matters
feedbackHow a reviewer responded to a specific finding, and why Rejections encode a judgment you cannot read off the codebase. The highest-value thing it stores.
conventionA team rule, also stored as a Hindsight directive Rules apply to every review. Similarity search is the wrong retrieval for a standing rule.
incidentA bug or outage tied to a code pattern Turns a post-mortem from a wiki page nobody reads into something that flags the next pull request.
reviewA summary of each review posted It knows what it already said.

It tells you what it chose not to say

Every review lists the suggestions it suppressed and the rule behind each. Silence is invisible otherwise: you cannot tell a reviewer that learned from one that got distracted.

Where memory changes the outcome

Institutional memory survives people

The engineer who knew why you don't do X leaves. The rejection they recorded stays, and keeps shaping reviews after they're gone.

Post-mortems become prevention

An incident stops being a document nobody reads and becomes a rule that flags the next change repeating the pattern.

Onboarding compresses

A new joiner's first reviews already carry house style, because the bot learned it from everyone who came before.

Review fatigue reverses

Teams disable review bots when noise beats signal. This one gets quieter and more specific over time instead of louder.

Using it

What it feels like after a week

The behaviour changes in three stages, and you can watch it happen.

  1. First review. Generic. Indistinguishable from any other tool, because the bank is empty and it has nothing to go on.
  2. After the team answers. One suggestion accepted, one rejected, two conventions stated. Three memories exist.
  3. Second review, different file. Every finding cites the rule behind it, and the rejected suggestion is listed under what it deliberately did not raise.
  4. After an incident is recorded. A later change with the same shape of bug gets flagged high severity, naming the outage and what it cost.

Ask it directly what it has learned:

$ memolint ask "what does this team care about in reviews?"

What we learned

Things that surprised us building it

Written up honestly, including the mistake that nearly made it into a published result.

Our A/B test was measuring two models

The memory-off half ran on one provider and the memory-on half fell back to another after a rate limit. The comparison looked great and proved nothing. Both halves are now pinned to one provider, and the run warns if they ever differ.

Rejections beat acceptances

An accepted suggestion tells you the reviewer was already right. A rejection encodes a judgment that exists nowhere in the code.

Rules and facts need different retrieval

A team convention should apply whether or not the diff looks familiar. Putting rules in directives instead of similarity search fixed a whole class of inconsistency.

Tell the model how to match, not just what

One paragraph instructing it to match incidents on the shape of a bug rather than its wording changed behaviour more than any amount of extra context.

A test that passes slowly is a bug report

Our suite jumped to 68 seconds. A rate-limit test was busy-waiting a full minute, because sleep was mocked inside a loop that needed the clock to move.

Waiting on purpose beats being told to wait

Pacing requests against a rolling token budget is cheaper than retry backoff, and deterministic, which matters when anything downstream depends on timing.

Both write-ups go into more detail: on memory design and on the broken comparison.
